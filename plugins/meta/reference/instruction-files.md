# 指示ファイルとエージェントの判断

指示ファイル（CLAUDE.md、AGENTS.md、SKILL.md、rules、hooks、サブエージェントなど）が、エージェントの判断にどう効くかをまとめた資料。どこに置いたファイルがいつ読み込まれるか、サイズの上限、frontmatter の項目といった仕様は、クライアントとバージョンによって違い、更新も多いので、ここには書かず [sources.md](sources.md) から公式ドキュメントで確かめる。モデルの既定の振る舞いも世代によって変わるので、使っているモデルのプロンプトガイドを見る。

## 指示が判断になるまで

エージェントの行動は、そのときコンテキストにあったすべての指示と、モデルの既定の振る舞いと、目の前の状況を合わせたものから決まる。一つのファイルの文面だけでは決まらない。

指示は、コンテキストに入っていなければ書いていないのと同じである。入るかどうかは、ファイルの場所と名前、サブディレクトリのファイルが読み込まれる条件、プロジェクトの信頼設定や無効化の設定、サイズの上限、サブエージェントに渡るか、compaction のあとに戻るか、編集したあとセッションが読み直したかで決まる。たとえば、パスを指定した rules は、クライアントによっては compaction のあと、該当するファイルをもう一度読むまで戻らない。

skill や条件付きの指示は、エージェントが選んだときにだけ本文が読まれる。選ぶときに見ているのは description と適用条件だけなので、依頼で使われた言葉と合っていなければ選ばれず、範囲が広すぎたり言い方が強すぎたりすれば関係のない場面でも選ばれる。migration 用の skill の description に「データベースを扱うとき」と書くと、クエリを少し直すだけの依頼でも読み込まれる。

多くのクライアントは指示をつなげて渡すだけで、矛盾していても解消しない。ユーザー全体の指示に「変更の前に確認する」、プロジェクトの指示に「テストは確認なしで実行してよい」とあり、テストの失敗を直す変更がどちらに当たるか書かれていなければ、エージェントは毎回違う判断をしうる。重複、理由の抜け、強調の偏り、曖昧な書き方も、同じように判断を揺らす。

エージェントは書かれた指示に従い、書かれた理由を似た場面にも当てはめる。規則だけを書くと、書き手が思いついた場面にしか当てはまらない。手順を書くと、エージェントは状況を見て計画を立てる代わりに手順を上から実行し、手順が想定していない状況でもそのまま進めて失敗する。条件と行動の対応を並べた指示も同じで、並べた条件の外では何を良しとするかが伝わらない。

## 何を書くと判断が良くなるか

判断の材料になるのは、次のようなことである。

- 完了の条件と、それを確かめる方法。テストやスクリプトなど照らし合わせられるものがあれば、確かめ方の手順は要らない。やり方を細かく書きたくなるのは、たいてい完了の条件がはっきりしていないときである。途中で止めてユーザーに確認させる指示は、エージェントが続けてよい場面でもそこで止まる原因になるので、本当に判断が要る箇所にだけ置く。
- どのやり方を選んでも守るべき制約と、その理由。理由があれば、書かれていない場面にも当てはめられるし、前提が変わったときに外してよいかも判断できる。制約が多いほど、ぶつかったときの優先が要る。
- 状況をどう捉えるか、何を良しとするかという考え方。
- 状況を見ても分からない事実。例: 「フィーチャーフラグは管理画面で切り替えているので、コードを見ても今の値は分からない」。

書き方について。

- してほしいことを書いた指示のほうが伝わる。「〜しない」は、本当に避けなければならないことのためにとっておく。
- MUST や太字や「必ず」は、多用すると、どれが本当に大事なのか区別がつかなくなる。関係のない場面でも過剰に反応したり、続けてよい場面で止まったりする。
- ほかの文書を読ませるなら、どの場面でどれを読むかが要る。「作業の前に毎回読む」は、関係のない作業でもコンテキストを使う。
- 例は出力の形をそろえるのには役に立つが、どう判断するかは例からは伝わりにくい。

手順が役に立つのは、少し間違えると壊れる操作、毎回同じ結果が必要な処理、順番を守らないと失敗する処理である。その場合も、なぜその順番なのかがあれば、想定外の状況で外してよいかを判断できる（「タグを先に打つ。CHANGELOG がタグを参照するため」）。

一文の要否は、新しく入った有能な同僚への説明にそれを含めるかで考えられる。

## 仕組みが何をするか

| 仕組み | コンテキストに入るとき、働き |
|---|---|
| 常に読み込まれる指示ファイル（CLAUDE.md、AGENTS.md など） | 毎回入る。そのぶん常にコンテキストを使う |
| パスを指定した rules、サブディレクトリの指示ファイル | 該当するディレクトリのファイルを扱うときに入る |
| skill | 普段は description だけが入り、本文は選ばれてから読まれる |
| hooks、permissions | コンテキストではなくクライアントが実行し、エージェントの判断にかかわらず、決まった操作を実行する、または止める。エージェントがそうしようとした判断そのものは変えない |
| subagent | 別のコンテキストで動く。親の指示ファイルや memory が渡るかは、種類とクライアントによる |
| memory | セッションをまたいで残る。読まれて従われることは保証されない |
| output style | 応答の形式を、会話のあいだずっと決める |

仕組みがあるかどうかも細かい動きも、クライアントによって違う。

## 指示を足すことの費用

- 何も書かなくてもモデルがする振る舞いを書くと、過剰になる。控えめに書くと、書いたとおり控えめにしか動かない。
- repo に置いた指示は、別のクライアントや別のモデルを使う人のエージェントも読む。あるモデルの癖を抑えるための強い言い方や確認の指示は、別のモデルでは止まりすぎや余計な確認になる。
- 個別の事例を書き足すと、ほかの指示が読まれにくくなる。受けたフィードバックは、何かの理由の一例であることが多い。その理由がすでに書いてあるなら、足りないのは文ではない。
- 消してもエージェントが間違えない文は、コンテキストを使うだけである。直ったバグ、消えたコード、ほかへ移した内容についての文は、いずれそうなる。
- 書き足すほかに、置き場所を変える、既存の文とまとめる、矛盾している文を消す、という直し方がある。今の構成が正しいとは限らず、モデルが賢くなれば要らなくなる指示もある。

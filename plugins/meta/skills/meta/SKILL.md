# 指示ファイルを書く・直す

このスキルは、指示ファイルを新しく書くとき、手を入れるとき、指示どおりに動かない原因を調べるときに使う。どの場合も、まず次の節のとおり仕様を確認する。作業がどこで終わるかは、最後の「終わりの条件」に書いた。

## 仕様は毎回ドキュメントで確認する

どこに置いたファイルがいつ読み込まれるか、複数のファイルがどう組み合わさるか、サイズの上限、frontmatter の項目は、クライアントとバージョンによって違い、更新も多い。覚えている内容で答えず、[reference/sources.md](reference/sources.md) から公式ドキュメントを開いて確認する。モデルがデフォルトでどう振る舞うかも世代によって変わるので、使っているモデルのプロンプトガイドを見る。

## 何を書くか

エージェントは書かれた指示に従い、書かれた理由を似た場面にも当てはめる。規則だけを書くと、書き手が思いついた場面にしか当てはまらない。手順を書くと、エージェントは状況を見て計画を立てる代わりに手順を上から実行し、手順が想定していない状況でもそのまま進めて失敗する。

指示ファイルに書くのは、次のようなことにする。

- 完了の条件と、それを確かめる方法。テストやスクリプトなど照らし合わせられるものを渡せば、確かめ方の手順は要らない。やり方を細かく書きたくなったら、完了の条件がはっきりしているかを先に見直す。途中で止めてユーザーに確認させる指示は、そこで本当に判断が要るときだけにする。止める箇所を書くと、エージェントは続けてよい場面でもそこで止まりやすい。
- どのやり方を選んでも守るべき制約と、その理由。理由があれば、書かれていない場面にも当てはめられるし、前提が変わったときに外してよいかも判断できる。数は少なくする。制約同士がぶつかりうるなら、どちらを優先するかも書く。
- 状況をどう捉えるか、何を良しとするかという考え方。
- 状況を見ても分からない事実。例: 「フィーチャーフラグは管理画面で切り替えているので、コードを見ても今の値は分からない」。

書き方について。

- してほしいことを書く。「〜しない」という書き方は、本当に避けなければならないことにだけ使う。
- MUST や太字や「必ず」は、実際に危険なところにだけ使う。多用すると、どれが本当に大事なのか区別がつかなくなり、関係のない場面でも過剰に反応したり、続けてよい場面で止まったりする。
- ほかの文書を読ませたいときは、どの場面でどれを読むかを書く。「作業の前に毎回読む」と書くと、関係のない作業でもコンテキストを使う。
- 例は出力の形をそろえるのには役に立つが、どう判断するかは例からは伝わりにくい。

手順を書くのは、少し間違えると壊れる操作、毎回同じ結果が必要な処理、順番を守らないと失敗する処理に限る。その場合も、なぜその順番なのかを書く（「タグを先に打つ。CHANGELOG がタグを参照するため」）。毎回確実に実行させたいなら、文章ではなく hook やスクリプトにする。

迷ったら、その一文を、新しく入った有能な同僚への説明に含めるかを考える。

## 直すときに確認すること

- 何も書かなくてもモデルがする振る舞いではないか。すでにすることを書くと過剰になる。控えめに書くと、書いたとおり控えめにしか動かない。
- 誰のエージェントが読むか。repo に置いた指示は、別のクライアントや別のモデルを使う人のエージェントも読む。あるモデルの癖を抑えるために足した強い言い方や確認の指示は、別のモデルでは止まりすぎや余計な確認につながる。
- その一文を消したら、エージェントが間違えるか。間違えないなら書かない、または消す。すでにある文にも同じことを問う。直ったバグ、消えたコード、ほかへ移した内容についての文は、消しても困らなくなっている。
- 受けたフィードバックが、どういう理由の一例なのかを考える。その理由がすでに書いてあるなら、足りないのは文ではなく、その理由が読まれなかった原因のほうである。個別の事例を書き足すと、ほかの指示が読まれにくくなる。理由のほうを直し、事例は書かない。
- 今ある指示の一つずつについて、文章で足りるかを見る。毎回必ず実行させたいことや絶対にさせたくないことを文章で頼んでいたら、次の「どの仕組みに書くか」に沿って hook や permissions に移す。
- 末尾に書き足す前に、置き場所を変える、既存の文とまとめる、矛盾している文を消す、を先に考える。今の構成が正しいとは限らない。モデルが賢くなれば要らなくなる指示もある。

## どの仕組みに書くか

必要な場面でコンテキストに読み込まれていない指示は、書いていないのと同じである。いつ、どのくらい確実に守らせたいかで仕組みを選ぶ。

| 守らせたいこと | 仕組み |
|---|---|
| いつも守らせる短い原則や注意点 | 常に読み込まれる指示ファイル（CLAUDE.md、AGENTS.md など）。常にコンテキストを使うので短くする |
| 特定のディレクトリで作業するときだけ必要なこと | パスを指定した rules、そのディレクトリに置く指示ファイル |
| 呼び出したときだけ必要な知識や作業 | skill。普段読み込まれるのは description だけで、本文は呼び出されてから読まれる |
| 必ず実行する、または絶対に実行させないこと | hooks、permissions。文章の指示では保証できない |
| 別のコンテキストでさせたい作業 | subagent。親の指示ファイルや memory が渡るかは、種類とクライアントによる |
| セッションをまたいで覚えておくこと | memory。必ず守らせたいルールには使わない |
| 応答の形式 | output style |

仕組みがあるかどうかも細かい動きも、クライアントによって違う。書く前にドキュメントで確認する。

## 期待どおりに動かないとき

指示が実際の動きになるまでには、次の 4 つの段階がある。どこで止まったかを、前の段階から順に確かめる。前の段階で止まっているなら、文面を直しても変わらない。推測で直さず、クライアントが用意している確認手段（読み込まれたファイルの一覧、デバッグログ、セッションのログ）で確かめる。

1. 読み込まれていたか。エージェントが判断したとき、その指示はコンテキストにあったか。ファイルの場所と名前、サブディレクトリのファイルが読み込まれる条件、プロジェクトの信頼設定や無効化の設定、読み込めるサイズの上限、サブエージェントに渡っていたか、compaction のあとに戻っていたか、ファイルを編集したあとセッションが読み直したかを見る。たとえば、パスを指定した rules は、クライアントによっては compaction のあと、該当するファイルをもう一度読むまでコンテキストに戻らない。
2. 選ばれたか。skill や条件付きの指示が使われたか。エージェントが選ぶときに見ているのは description と適用条件だけである。依頼で使われた言葉と合っているか、似た description のスキルと取り合っていないか、範囲が広すぎないか、強い言い方のせいで関係のない場面でも使われていないかを見る。たとえば、migration 用の skill の description に「データベースを扱うとき」と書くと、クエリを少し直すだけの依頼でも読み込まれる。
3. どう解釈されたか。動きは一つのファイルではなく、そのとき読み込まれていたすべての指示を合わせたものから決まる。多くのクライアントは指示をつなげて渡すだけで、矛盾していても解消しない。その動きにつながりそうな文をすべてのファイルから集めて並べ、矛盾、重複、理由の抜け、デフォルトの振る舞いとの重複、強調の偏り、曖昧な書き方がないかを見る。たとえば、ユーザー全体の指示に「変更の前に確認する」、プロジェクトの指示に「テストは確認なしで実行してよい」とあり、テストの失敗を直す変更がどちらに当たるか書かれていなければ、エージェントは毎回違う判断をしうる。
4. 仕組みの選び方が合っていたか。確実に守らせたいことを文章で頼んでいないか、一部の作業でしか要らないことを常に読み込んでいないか、作業のあいだずっと守らせたいことを一度しか読まれない場所に書いていないかを見る。たとえば、「本番のデータベースに書き込まない」を文章で頼んでも保証にはならない。保証が要るなら、permissions や hook で書き込みを拒否する。

調べた結果、仕様どおりの動きで、設定した人の意図にも合っていることもある。自動で使われないように設定された skill が自動で使われない、などである。その場合は直す案ではなく、そう考えた根拠と、意図が違うなら何を変えればよいかを示す。

直す案を出すときは、どの段階の問題か、何を見てそう考えたかを添える。主語が抜けている、同じものを違う言葉で呼んでいる、といった細かい問題も一緒に直すが、先に直すのは仕組みや構成の問題である。

「どうすればいい？」「なんか違う」のように答えが決まっていない相談では、一般論で終わらせず、今どう動いているかを調べて仮説を立て、ユーザーと話しながら決める。ユーザーの指示がいつも正しいとは限らないので、エージェントが意図どおり動くかを基準にして、根拠を示して別の案を出す。

## 終わりの条件

原因を調べる依頼は、どの段階で止まっていたかを、確認手段の結果か公式ドキュメントの記述を根拠に示し、直す案か、直さなくてよい理由を出したところで終わる。確認手段を実行できない環境なら、何を実行すれば確かめられるかも示す。

書く・直す依頼は、変更したうえで、実際にエージェントを動かして期待どおりになったことを確かめたところで終わる。直した指示が正しいかどうかは、動かしてみるまで分からない。動かせない環境なら、どう試せばよいかを示す。調べてから直す依頼は、調べる依頼の条件を満たしたうえで、こちらの条件で終える。試すときは次を見る。

- 使われるはずの依頼で使われ、関係のない依頼では使われないか。新しいセッションで試す。
- 失敗した事例をもとに書いた文は、その事例で試せばうまくいくに決まっている。同じ理由が当てはまる別の場面で試す。
- 構文のチェック、使用状況の確認、使われ方と出力の評価には、クライアントが用意しているツールを使う。
- 頼まれた範囲の外に書き足していないか。

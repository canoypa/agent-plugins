# retrospective

このスキルは、レトロスペクティブの前半を行う。セッションで期待と違ったところと、うまくいったところを集め、そうなった判断をログから書き起こして、振り返りとして残す。何を変えるかを決める後半は、harness-improve が別のセッションで、ほかの振り返りと並べて行う。前半と後半を分けるのは、一度だけでは偶然か繰り返しか分からないからである。

あなたは、振り返る対象のセッションの当事者ではない。そのタスクをしたセッションは、自分の動きを俯瞰するのに向かず、長い会話では compaction で前半を要約でしか持っていない。だから振り返りは、会話を持たない別のエージェントが、ログ全体を読んで書く。対象のログは `~/.claude/projects/*/${CLAUDE_SESSION_ID}.jsonl` で、引数にセッション ID が渡されたらそちらを読む: $ARGUMENTS

ログは既定で 30 日ほどで消えるが、振り返りは残り、後半はそれを読む。後半が要るものは、ここで振り返りに書き写しておく。

## 集める

集めるのは、評価ではなく、起きたことである。ユーザーの発言やツールの結果のように、ログで確かめられる観測で書く。

ログから、訂正、却下（拒否されたツール実行を含む）、やり直しのように言われたものだけでなく、言われていないが手戻りしたこと、使われるはずのスキルや守られるはずの指示が働かなかったことも集める。その場限りに見えるものも残す。繰り返すかどうかは、振り返りが集まってから分かる。ユーザーがはっきり良いと言った判断も、何がうまくいったかの材料として集める。

一件ごとに、次を書く。

- 何が起きたか: 順を追って書き、ユーザーの発言は引用する
- ユーザーが何を期待していて、実際とどう違ったか
- 誰が気づいたか: 「ユーザーの指摘」「自分で気づいた」「ツールの失敗」「振り返りで見つけた」のどれかの語で書き始める。最後のものは、セッションの中では誰も気づかず、ログを読んで初めて分かった件。harness-improve が件をまたいで数える
- ログのどこか: セッション ID と、その件の最初のユーザーの発言の時刻。ログが残っているうちは、後半がここから確かめ直せる

## 判断を書き起こす

集めた件ごとに、期待と違う動きになった判断を、その時点に戻って書き起こす。後半が探すのは、同じ判断が繰り返される理由である。指示が届いていたか、だけでは、届いていたのに起きた件で「もっと強く止める」しか打てる手が残らない。その判断が何を見て、何を良しとしてなされたかが分かれば、違う作業で起きた件どうしが同じ判断から来ているかを並べて見られる。

- その時点で何を知っていたか: 見ていた情報、自分で確かめていたこと、ユーザーの発言をどう受け取ったか
- 何を目指し、何を優先したか。なぜそれでよいと思ったか
- 期待と、どの判断から分かれたか

判断は、ログに表れたアシスタントの発言とツールの使い方から起こす。そのセッション自身の振り返りや要約は、その時の判断と食い違うことがある。たとえば「確かめなかった」とされていた件で、実際には確かめて危うさを書いたうえで、ユーザーの「ok」を許可と読んで進めていた、ということがある。思考の中身はログで読めないことが多いので、表に出た文から読み取ったところは推測だと書く。

直し方は書かない。規則や処方の形で書くと、後半はその件に蓋をする案を読み取り、判断の中身を見なくなる。同じ理由で、振り返りの場で memory や指示ファイルを直さない。

分かれた判断が一つで、そこから期待と違う動きがいくつも続いたなら、一件にまとめる。

## 残す

後半の harness-improve は、次の形を前提に振り返りを読む。

- そのタスクの記録（作業ログなど）の隣に置く。置き場所はユーザーの指示ファイルと、ログの中でそのセッションが書いた作業ログから決める。決められなければ書かずに、振り返りの本文を呼び出し元に返す
- 名前は `retrospective.md` で終わり、ほかの振り返りと重ならないものにする。付け方はユーザーの指示に従い、決まりがなければタスクの名前を頭に付ける
- 先頭に、日付と何の作業のセッションかを書く
- 一件を一つの `##` 見出しにし、見出しはファイルの中で重ねない
- harness-improve が件を `[[<拡張子を除いたファイル名>#<見出し>]]` で指すので、書いた件は書き換えない
- 同じタスクの振り返りがすでにあれば、新しく作らず、その末尾に日付を添えて件を足す

集めるものがなければ、何も残さずにそう伝える。書いたら、ファイルの場所と件の見出しを呼び出し元に返す。
